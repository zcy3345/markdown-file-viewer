# 环境与工具链（2026-11-14 实测）

这份文档记录"在这台机器上把 mdv 做出来"踩到的环境坑和实测数据。改代码前先看这里，
别把已经绕过的问题再踩回去。

## 1. Rust / MSVC：默认 toolset 是坏的

**症状**：任何 `cargo build` 都失败，报错极具误导性：

```
link: extra operand '...rcgu.o'
note: in the Visual Studio installer, ensure the "C++ build tools" workload is selected
```

**根因**（三层叠加）：

1. `<VS Build Tools 目录>\VC\Auxiliary\Build\Microsoft.VCToolsVersion.default.txt` 写的是 `14.51.36231`，
   而 `VC\Tools\MSVC\14.51.36231\` 下**只剩 `Auxiliary\`**（安装不完整）。
2. 于是 `vcvarsall.bat x64` 把不存在的 `...\14.51.36231\bin\HostX64\x64` 写进 PATH，rustc 找不到 linker，
   回落到 PATH 里的 `E:\git\Git\usr\bin\link.exe`（GNU coreutils 的 `link`，直接报 extra operand）。
3. `cl.exe` 也不在 PATH，所以凡是带 C 代码的 crate（`onig_sys` 等）在 cc-rs 阶段就死。

**已落地的绕过**：全局 `%USERPROFILE%\.cargo\config.toml`，显式指向完整的 14.44.35207：

```toml
[target.x86_64-pc-windows-msvc]
linker = "<VS Build Tools 目录>/VC/Tools/MSVC/14.44.35207/bin/HostX64/x64/link.exe"
[env]
LIB     = ".../14.44.35207/lib/x64;<Windows SDK 目录>/lib/10.0.28000.0/{ucrt,um}/x64"
INCLUDE = ".../14.44.35207/include;<Windows SDK 目录>/Include/10.0.28000.0/{ucrt,um,shared,winrt,cppwinrt}"
CC / CXX = ".../14.44.35207/bin/HostX64/x64/cl.exe"
AR       = ".../14.44.35207/bin/HostX64/x64/lib.exe"
RC       = "<Windows SDK 目录>/bin/10.0.28000.0/x64/rc.exe"
```

效果：不 source 任何 vcvars、在任意 shell 里 `cargo build` 都可用，含 C 依赖（`onig_sys` 实测通过）。

**根治**（需要 GUI + 管理员，待做）：VS Installer → 修复 `<VS Build Tools 目录>`，让 14.51 / 默认 toolset 变完整。
修好之后这份 config 仍能用（只是锁在 14.44）。

其他环境事实：
- Windows SDK 在 **`<Windows SDK 目录>`**（10.0.28000.0），不是标准的 `C:\Program Files (x86)\Windows Kits` —— 脚本里别硬编码。
- VS 2026 的 vcvars 脚本是 `vcvarsall.bat x64 [-vcvars_ver=14.44]`，**没有 `vcvars64.bat`**。
- `rustup` 自更新（1.29.0 → 1.29.3）报 `os error 2`；工具链本身是最新的 1.95.0，不影响编译。

## 3. 实测性能（Rust 管线，release，重复 2 次一致）

| 项目 | 耗时 |
|---|---|
| comrak 1.0.0-rc.1 解析 + 渲染 spec.md 全篇 | **0.3–0.4 ms** |
| syntect SyntaxSet + ThemeSet 加载 | 1.5 ms（"预热成本"担心不成立）|
| syntect 首次高亮每种语言 · `regex-onig` | **1.8–2.9 ms** |
| syntect 首次高亮每种语言 · `default-fancy` | **23–37 ms（慢 12 倍）** |
| syntect 同语言第二块（warm） | 0.2–0.5 ms |
| release 二进制 | ~3.3 MB（含 75 种 syntax）|

**结论**：Rust 版的 60–120 ms 目标**只在 `regex-onig` 下成立**。若为了"用户机器没有 C 编译器也能构建"
而选纯 Rust 的 `default-fancy`，4 种语言的文档要 ~130 ms，比 Node 原型（53–66 ms）还慢。
→ 发布版固定 onig + 预编译二进制，不让终端用户自己 build。

## 7. Rust 版（Rust 实现）实现备忘

位置 `mdv/`，单文件 `src/main.rs`，二进制约 2.1 MB。管线：
comrak -> syntect 高亮 -> 相对路径重写 -> 内联 mdv.css + 共享 KaTeX 资产 -> 写临时 HTML -> Edge 开窗。

**实测**（release，spec.md）：

| 阶段 | 耗时 |
|---|---|
| comrak 解析 + 渲染 | 0.3–0.5 ms |
| syntect 高亮（6 个代码块、4 种语言、进程内首次加载语法集） | 13.8–14.3 ms |
| 写盘 | 0.4–0.6 ms |
| **合计** | **15.4–18.5 ms** |

对比 Node 原型纯渲染 53–66 ms（不含 Node 启动 71–98 ms）。

### comrak 1.0.0-rc.1 的 API 与旧文档不一致处

1. `markdown_to_html(md, &options)` **返回 String**（2 参）；要写缓冲区得用 `parse_document` + `format_html`。
2. `Options<'c>` 带生命周期。
3. `extension.header_ids: Option<String>` **已改名** 为 `header_id_prefix: Option<String>`（空串 = 无前缀 id）。
4. `render.unsafe_` 改名为 `render.r#unsafe`。
5. tasklist 复选框即使 `unsafe = false` 也会输出 `<input type="checkbox" disabled>`。

### 数学：走 comrak 的 math_dollars

```rust
options.extension.math_dollars = true;  // $x$ / $$x$$ -> <span data-math-style="inline|display">
```

页面里 KaTeX 由 `katex.min.js`（从 `node_modules/katex/dist` 内联，CSS 的 `url(fonts/…)`
改写成 `file:///` 绝对路径）在浏览器端渲染 `[data-math-style]` 元素，latex 从 `el.textContent` 取。

**坑**：不要自己用正则从 Markdown 源码里抠 `$…$` —— markdown 会把 `&` 转义成 `&amp;`，
```\begin{pmatrix} a & b \\ c & d\end{pmatrix}``` 这类结构会被渲染坏（表现为矩阵/分段函数错位、
残留 `$$`）。让 comrak 负责切分，页面负责渲染。

### 其他小坑

- `<pre>` 自己带 `>`：找 `<pre><code` 的标签结束符时必须从 `<code` 之后再找，否则会把 `<code …>` 当正文。
- `fs::canonicalize` 在 Windows 返回 `\\?\F:\…` verbatim 路径，直接转 URL 会变成 `file://///%3F/F:/…`，
  必须先剥前缀。
- comrak 先把文本转义、href 先百分号编码：高亮前要解码实体，重写 URL 前要百分号解码（中文/空格路径）。
- 语法集/主题用 `once_cell::Lazy` 进程内只加载一次（1.5 ms，其实很便宜）。

## 8. 交付物纯净策略（运行端只有 exe + Edge）

**目标**：用户端不装 Node、不装 Python、不需要 node_modules、不跑后台服务。一个 exe 拷过去就能用。

### 编译期塞进二进制的资产

| 资产 | 来源 | 大小 |
|---|---|---|
| comrak + syntect（75 种语法 + 主题 dumps）| crate | — |
| `mdv.css` | `include_str!` | 4.5 KB |
| `katex.min.css` / `katex.min.js` | `include_str!`（vendored 到 `assets/katex/`）| 24 KB + 272 KB |
| 20 个 `.woff2` 数学字体 | build.rs 生成 `include_bytes!` 表 | 254 KB |

```
mdv/build.rs  扫描 assets/katex/fonts/*.woff2 -> OUT_DIR/fonts_table.rs
```

结果：`mdv.exe` = **5,527,040 字节（5.27 MiB）**。

### 运行期写到磁盘的地方（3 类，全在 `%TEMP%\mdv\`）

| 路径 | 内容 | 触发 |
|---|---|---|
| `%TEMP%\mdv\view-<pid>.html` | 本次渲染的页面（约 23 KB）| 每次打开；下次运行清理 5 秒前的残留 |
| `%TEMP%\mdv\mdv.ico` | 文件类型图标 7.9 KB | 缺失或长度不符时自愈 |
| `%TEMP%\mdv\assets\` | KaTeX js/css + 20 个数学字体（约 0.5 MB）| 首次运行，长度自愈 |

`%LOCALAPPDATA%` 下**没有**任何 mdv 目录。`--shot` 会额外用 `%TEMP%\mdv-shot-<pid>` 作浏览器 profile，跑完立即删除。

### 验证方式（别只信声明）

```powershell
cd "<repo>"
Rename-Item node_modules node_modules.bak      # 让运行环境彻底没有 node
Remove-Item "$env:LOCALAPPDATA\mdv" -Recurse -Force
.\mdv.exe spec.md --shot pure.png --size 940x3400
```

在**空目录**里只放 `mdv.exe` + `spec.md` 也能出完整页面（实测过：数学字体、代码高亮、行号、脚注全部正常）。

### 无法"纯粹"的部分：构建

Rust 必须有链接器：rustc/cargo + MSVC（`link.exe`/`lib.exe`/`cl.exe`）+ Windows SDK。
这是**编译机器**上的依赖，不进交付物。想连这个都免只能走 `x86_64-pc-windows-gnu` 交叉编译（换 mingw，另一种污染），不划算。

vendored 资产（`assets/katex/`）算"仓库里的第三方文件"，不是工具链：`cargo build` 不会去联网装它，
也不需要 npm 参与。

## 10. 文件关联（被动模式）实施记录

- 命令：`mdv.exe --install [--no-default]` / `--uninstall` / `--status`
- 实现：纯 `reg.exe` 调用（无新 crate），全在 HKCU，不需要管理员。
- 图标：`assets/mdv.ico`（PowerShell + System.Drawing 生成，6 个尺寸 PNG-in-ICO），
  ```include_bytes!``` 进 exe，安装时解到 ```<LOCALAPPDATA>\mdv\mdv.ico```。
- 卸载会读 `HKCU\Software\mdv\PrevMdDefault` 把 .md 默认值还原，避免把机器留成半坏状态。

坑：

1. **Git Bash 会把 `/s`、`/ve` 这类参数当路径转换** —— 在 bash 里手敲 `reg query` 必须
   ```export MSYS_NO_PATHCONV=1```，否则报"无效语法"。Rust 里直接 ```Command::new("reg")``` 传参数没有这个问题。
2. **不要按 CommandLine 找 Edge 窗口进程** —— Edge 已运行时新 `--app` 窗口由已有进程创建，
   新进程命令行里没有 URL。按 `MainWindowTitle` 找（`Get-Process msedge | Where MainWindowTitle -like '*文件名*'`）。
3. PowerShell 脚本存成 UTF-8 **无 BOM** 时，PS 5.1 按 ANSI 读，中文字符串会被截断成语法错误。
   项目里的 .ps1 一律带 BOM（`tools/fix-machine-path.ps1`、`ref/dblclick-test.ps1`）。
4. 改了关联后图标要等资源管理器刷新：`ie4uinit.exe -show`（已内置调用），不行就重启 explorer。

## 13. 三份独立审计（2026-11-14）与修复

对 mdv.exe 做了三路只读审计：进程/内存驻留、磁盘增长、源码审查。结论与修复如下。

### 结论

| 问题 | 结论 |
|---|---|
| 后台偷偷吃内存？ | **没有**。mdv.exe 是一次性进程：0.155 s 退出，峰值工作集 2.6–6 MB，常驻 0；三个 `Run` 键、服务、计划任务里 0 命中；渲染过程完全不写注册表 |
| 后台偷偷占磁盘？ | **没有无界增长**，但有浪费：每个缓存 HTML 曾固定 308.5 KB（内联 katex.min.js 272 KB）→ 200 个 = 61.7 MB；上限只数字数不按体积 |
| 进程残留？ | mdv 侧干净；Edge 为 app 窗口起的 4 个 renderer（约 240 MB）**关窗后仍存活**，直到 Edge 整体退出 —— 这是 Edge 行为 |

### 审计发现 → 修复

| # | 问题（证据） | 修复 |
|---|---|---|
| 1 | 缓存 HTML 每篇内联 272 KB katex.min.js → 200 篇 61.7 MB | KaTeX js/css 改为共享文件（`assets/katex-0.16.47/`），页面用 `<link>`/`<script src>` 引用 → **23 KB/篇，200 篇 ≈ 4.6 MB** |
| 2 | 非原子写：进程被杀留半截文件，而命中只看"文件存在" → 坏页面永久命中（实测截断 5 字节仍 cache hit）| 写临时文件 + rename（`write_atomic`）+ 命中校验尾部 `</body></html>`；字体校验"长度等于内嵌字节数" |
| 3 | 缓存上限只按条数（200 × 数 MB 无上限）| 同时限 **64 MB** 总量 |
| 4 | `--shot` 用固定 `%TEMP%\mdv-shot-profile`，从不清理（实测遗留 70 MB），并发必失败（exit 21），`.status()` 无超时会挂死（实测 `--size 0x0` 挂 62 s）| 每次用 `mdv-shot-<pid>`、跑完 `remove_dir_all`、**20 s 超时后 kill** |
| 5 | `--size 0x0` 不校验 | 拒绝 0 与 >10000 |
| 6 | `reg_read_default` 用 UTF-8 解 reg.exe 的 GBK 输出 → `--uninstall` 会把含中文的原默认值写成 U+FFFD | 改用 Win32 `RegGetValueW` 直接读 UTF-16（`windows-sys`）|
| 7 | README 写了 `FriendlyAppName` 但代码没写；`--size` 对开窗无效（硬编码 940×1080）| 补写 `FriendlyAppName`；`launch()` 接收 `args.size` |
| 8 | 图标被删后不自愈（清 `%LOCALAPPDATA%\mdv` 时把 `mdv.ico` 删了，注册表指向失效路径）| `ensure_icon()`：每次运行检查 7.9 KB 图标，缺失即重写 |
| 9 | 代码块语言名未转义（依赖 comrak 的转义保证）| 显式 `escape_html` |
| 10 | 缓存键含 mtime 但不含大小 → `cp -p` 之类保持 mtime 的替换会命中旧缓存 | 键里加入源文件字节数 |

### 修复过程中的自伤（记一笔）

`cache_is_valid` 第一版写错：`seek(End(-15))` 却 `read_exact(16 字节)` → 永远 Err，
于是**缓存永不命中**、每次都重渲染。被"热缓存 17 ms 而不是 1.8 ms"这个异常数字抓出来。
教训：这种"看起来正常、其实是退化"的 bug，只有盯住**数字指标**才能发现。

### 修复后实测

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 单篇缓存 HTML | 308.5 KB | **23.2 KB** |
| 200 篇缓存占用 | 61.7 MB | **≈4.6 MB**（且 64 MB 硬上限）|
| 缓存命中 | 3.2 ms | **1.8 ms** |
| 截断的缓存/字体 | 永久损坏 | 自动重渲染 / 重写（实测恢复）|
| `--shot` 残留 | 70 MB 永久 | 0（跑完删除）|
| `--size 0x0` | 挂 62 s | 立即报错 |
| `--status` 中文 | 乱码 | 正常 |

## 14. 去掉缓存：改成无状态（2026-11-14）

用户要求："不要留缓存，这就是个 exe，默默呆着。"

### 改法

| 项 | 之前 | 现在 |
|---|---|---|
| 渲染结果 | 按内容 hash 存 200 份，命中跳过渲染 | **每次打开都重新渲染**，只写一个 `view-<pid>.html` |
| 位置 | `%LOCALAPPDATA%\mdv\cache` | `%TEMP%\mdv\` |
| 清理 | LRU（200 个 / 64 MB）| 每次运行前删掉 **5 秒以上**的 `view-*.html`
| 缓存键 / SHA-1 / LRU 代码 | 有 | **全部删除**（净减约 120 行）|
| 字体 + KaTeX 资产 | `%LOCALAPPDATA%\mdv\assets` | `%TEMP%\mdv\assets`（一次性 2.5 MB，长度自愈）|
| 文件类型图标 | `%LOCALAPPDATA%\mdv\mdv.ico` | `%TEMP%\mdv\mdv.ico`（需重跑 `--install` 更新注册表路径）|
| `%LOCALAPPDATA%\mdv` | 存在 | **不再存在** |

### 代价与实测

| 场景 | 之前（命中）| 现在（每次渲染）|
|---|---|---|
| 打开 spec.md | ≈10 ms | **≈28 ms**（内部 8–18 ms）|
| 首跑（temp 干净）| — | ≈47 ms（内部 36.9 ms，含解压 2.5 MB 资产）|
| 磁盘常驻 | 缓存最多 64 MB | **2.5 MB**（一次性资产）+ 一个 23 KB 临时文件 |

多花 ~18 ms 换"零持久状态"，用户明确要这个取舍。

### 为什么还要写文件

Edge 只能打开 URL：`data:` URL 受命令行 32 KB 限制（页面含 272 KB 的 KaTeX 不可能塞进去），
named pipe 不被支持，本地 HTTP 服务会多一个常驻进程 + 可能触发防火墙。
所以必须落一个临时文件，能做的只是**把它变成真正临时的**：只留一个、下次运行就删。

极端情况下（5 秒内连开多篇）会短暂存在多个 `view-*.html`，属正常；下一次运行即清。

### 注意

- 60 秒后再刷新一个已打开的窗口会 404（文件已被清）。页面内容已加载在内存里，正常阅读不受影响。
- `%TEMP%` 被 Windows 磁盘清理清空后，下次运行会自动重新解压资产（≈37 ms 的一次性成本）。

## 15. 去掉双击时的黑框（console 子系统 → GUI 子系统）

**现象**：双击 .md 时，Windows 会先闪一个黑色控制台窗口。
**原因**：Rust 默认把可执行文件编译成 console 子系统（PE 头 Subsystem = 3），
Explorer 启动这类进程时会先给它分配一个控制台。

### 改法

```rust
#![cfg_attr(windows, windows_subsystem = "windows")]   // PE Subsystem = 2 (GUI)
```

但直接改成 GUI 有两个副作用，必须一起处理：

1. **从终端运行时输出会消失** → 启动时 @@AttachConsole(ATTACH_PARENT_PROCESS)@@ 挂回父控制台，
   @@--print@@ / @@--status@@ / @@--shot@@ 的输出照常可见。
2. **从 Explorer 启动时 stdout 是无效句柄，@@println!@@ 会 panic** → 引入 @@QUIET@@ 标志
   （用 @@GetStdHandle@@ + @@GetFileType@@ 判定 stdout 是否可用），所有输出走 @@say!@@ / @@say_err!@@ 宏；
   管道/重定向场景（bash 里 @@./mdv.exe x.md --print@@）句柄有效，输出不受影响。

### 顺带补的：无控制台时报错要能看见

以前双击一个 GBK 编码的 md，进程静默退出，用户完全不知道发生了什么。
现在 @@QUIET@@ 为真时用 @@MessageBoxW@@ 弹窗显示错误。

### 验证

| 检查 | 方法 | 结果 |
|---|---|---|
| 是否还是没有控制台 | 读 PE 头 @@Subsystem@@ 字段（@@opt+68@@）| **2 (GUI)** ✅ |
| 双击的错误路径 | @@explorer.exe gbk.md@@（真·双击父进程），轮询该 pid 的窗口 | 出现标题为 @@mdv@@ 的弹窗 ✅ |
| 双击的正常路径 | @@explorer.exe ok.md@@ | mdv 退出、Edge 窗口出现、无弹窗 ✅ |
| 终端输出是否正常 | bash 里 @@--print@@ / @@--status@@ / @@--shot@@ | 全部正常，退出码也正常 ✅ |

**为什么不用 @@ShowWindow(GetConsoleWindow(), SW_HIDE)@@**：控制台窗口在进程启动前就被创建并显示，
在 main 里隐藏属于事后补救，仍可能看到一闪。只有换子系统才是根治。

## 16. 代码高亮"看起来没了"的两个真因（2026-11-14）

用户反馈："没有代码高亮了"。查下来是两件事叠加，都跟"有没有颜色"无关，而是**看不清**和**不认识语言**。

### 原因 1：主题对比度太低

原来用 syntect 内置的 ``base16-ocean.dark``。它的调色板（关键词 `#b48ead` 淡紫、字符串 `#a3be8c` 灰绿、
注释 `#65737e` 深灰）放在 ``#0f1620`` 这张深色卡片上几乎糊成一片 —— HTML 里明明有 247 个
``<span style="color:…">``，肉眼就是"没高亮"。

**修复**：自带一个 tmTheme（``assets/mdv-dark.tmTheme``，GitHub-dark 调色板，与 mdv.css 一致），
用 ``ThemeSet::load_from_reader`` 加载；解析失败自动退回 base16-ocean.dark。
需要给 syntect 开 ``plist-load`` feature（否则 ``load_from_reader`` 不存在，报 E0599）。

修完统计：同一篇 spec.md 的 247 个 span 里出现 8 种颜色，其中关键词 `#ff7b72` 25 次、
字符串 `#a5d6ff` 27 次、函数名 `#d2a8ff` 23 次。

### 原因 2：语法集只有 75 种，缺一堆常用语言

syntect 的 ``default-syntaxes`` 实测只认识 31/55 个常见围栏标签。**缺的包括：**
``typescript`` / ``ts`` / ``tsx`` / ``toml`` / ``kotlin`` / ``swift`` / ``scss`` / ``less`` / ``ini`` /
``cmake`` / ``dockerfile`` / ``powershell`` / ``vue`` / ``svelte`` / ``graphql`` / ``proto`` / ``csharp``。
也就是说，写 ```ts`` 或 ```toml`` 的文档一直是纯文本 —— 用户看到的确实是"没有高亮"。

**修复**：换成 ``two-face``（bat 打包的语法集，200+ 语言）：
```rust
static SYNTAXES: Lazy<SyntaxSet> = Lazy::new(two_face::syntax::extra_newlines);
```
再加一张别名表（``csharp→cs``、``kt→kotlin``、``docker→dockerfile``、``shell→sh``、``ps→powershell``、
``golang→go``、``proto3→proto``、``text/plaintext/console→不高亮``）。

实测覆盖：**31/33**（剩下两个不是失败：markdown 与 cmake 的语法本来就只上两三种颜色）。

### 代价

| 项 | 变化 |
|---|---|
| exe | 4.67 MB → **5.52 MB**（语法集从 75 种变 200+）|
| 语法集加载 | 0.6 ms → **2.3 ms**（75 种 → 220 种，release 实测）|
| 高亮耗时 | spec.md（4 语言）14 ms → **25 ms**（新语法上下文更多，首语言编译更贵）；单语言小文档最贵的一次是 TypeScript ≈18 ms |
| 附加依赖 | ``two-face 0.5``（纯 Rust）+ syntect 的 ``plist-load``（引入 ``plist``/``quick-xml``）|

### 验证方法（避免自欺）

1. **别只看"有没有 span"**：统计"不同颜色数"，只有 1–2 种基本等于没高亮。
2. **别用 Rust 代码去测 YAML/HTML**：语法解析不到 token 是内容不匹配，会误判成"不支持"。
   每个语言要用贴合它的样例（见本次用的 33 条样例表）。
3. 语言覆盖要**直接查语法集**（``find_syntax_by_extension/token/name``），而不是渲染后猜。

## 17. 滚动位置记忆 + 浏览器兜底（2026-11-14）

### 17.1 位置记忆：全部在页面侧

**约束**：mdv 是"打开即退出"的一次性进程 —— 它没机会在你滚动时观察你，
所以"记住位置"这件事**不可能由 mdv.exe 自己做**（除非引入常驻/短驻进程，那就打破了设计）。

**做法**：把记忆交给页面自己，用 file:// 页面的 localStorage。

| 项 | 结论 |
|---|---|
| file:// 能不能用 localStorage | ✅ 能，origin 就是 file:// |
| 跨进程持久化 | ✅ 实测连续 3 次独立运行，后一次读到前一次的值 |
| 存储位置 | 浏览器自己的 profile（Default/Local Storage，几 KB），**不在 %TEMP%\mdv** |
| 我们的磁盘写入 | **0**（mdv 侧不写任何状态文件）|
| 我们的常驻进程 | **0** |

实现要点：

- key = 文档绝对路径（因为所有 file:// 页面共享同一个 origin）
- value = `{y, h, ts}`；文档高度变化 **>25%** 时按比例换算，否则用绝对像素
- 滚动停止 400 ms 后回写；`y < 40` 不记录；表最多 200 条，超出按 ts 丢最旧
- 恢复脚本放在 `</body>` 前**同步执行** → 首帧就在正确位置，看不到跳动
- `MDV_RESTORE=0` 时整段不注入，回到零状态

一次踩坑：占位符原本写成 `DOC = "__MDV_DOC__"`，替换带引号的 JS 字面量后变成
`DOC = ""C:\...""` → 整段脚本语法错误、静默失效。改成 `DOC = __MDV_DOC__`。

实测：

| 场景 | 结果 |
|---|---|
| 读出+解析+scrollTo（200 条 / 13 KB 最坏情况）| **0.4 ms** |
| 回写 | **0.1 ms** |
| 同一文档重开 | y=1500 → **恢复 1500** ✅ |
| 文档变长 2.4 倍后重开 | 2000/5678 → **恢复 4876**（=2000×13843/5678）✅ |
| HTML 体积 | +约 1.7 KB（24887 vs 23192）|

### 17.2 浏览器兜底：--app 找不到怎么办

原来只硬编码两个 Edge 路径，Edge 装在 D 盘或换浏览器就退化。现在：

```
1) 查注册表 HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\<exe>
   依次尝试 msedge / chrome / brave / vivaldi / chromium / opera
2) 查常见硬编码路径兜底
3) 都没有 -> 退回 cmd /c start（系统默认浏览器），并打印一行提示
```

- 主流 Chromium 系都支持 --app（无边框窗口），所以 Chrome/Brave/Vivaldi 也是同一套体验
- 真没有 Chromium 时用默认浏览器打开：**失去无边框窗口**（有地址栏/标签页），但内容照常
- `mdv --status` 现在会显示实际用的是哪个浏览器、位置记忆是否开启

```powershell
PS> .\mdv.exe --status
程序    : F:\...\mdv.exe
.md 默认 : mdv.Document
工作目录 : C:\Users\...\Temp\mdv（临时文件，无缓存）
```

无法兜底的情况：浏览器被组策略禁用 --app（退化成普通窗口，内容仍正常）、
或者系统里一个 Chromium 都没有（这时用默认浏览器）。

## 19. 长文阅读优化（2026-11-14，有依据的一次调整）

用户反馈：「大段大段字读得很累」。先查资料再改，依据如下。

### 查到的依据

| 来源 | 结论 |
|---|---|
| W3C **clreq**（中文排版需求）issue #555 的 NOT E 提案 | 正文行长参考值 **17–40 字**；为避免「频繁换行、串行」，横排最大行长**不宜长于 48 字** |
| clreq 社区与中文排版实践（行距议题 #562 等）| 正文**行高取字级的 1.5–1.8 倍**；**段落间距约一个行高**；**中文正文原则上不动字距**，该调的是行距与段间距 |
| Kindle 排版建议（Dubberly《Recommendations for Kindle》）| Kindle 默认行距**过紧**，small/medium 都不适合长时间阅读，建议默认就用最大的那档 |
| Gao & Han, *Initial Exploration of Ideal Line Length for Chinese Technical Text*（IEEE ProComm 2019）| 专门研究中文技术文本的理想行长（付费墙，只取方向：行长可调且个体差异大，但存在明显偏好的中位区间）|

### 对照诊断

| 指标 | 改前 | 判断 |
|---|---|---|
| 行长 | 46rem = 736px ≈ **43.3 汉字/行** | 超出 clreq 的常见区间（17–40），接近上限 48 |
| 行高 | 1.8 | 在 1.5–1.8 的上限，勉强合格 |
| 段间距 | .95em = 16px = **0.53 个行高** | 远低于「约一个行高」，长文里段落糊成一片 —— 这才是「读得累」的主因 |
| 字距 | 正文未设 | ✅ 正确（中文不该调字距）|

### 试了三个变体

| 变体 | 行长 | 段间距 | 行高 | 结果 |
|---|---|---|---|---|
| V1 | 40rem（37.6 字）| 1.25em | 1.8 | 明显变好，但段落仍偏紧 |
| V2 | 38rem（35.8 字）| 1.55em | 1.85 | 更松弛，但出现孤字换行（「删掉。」单独一行）|
| **V3（采用）** | **40rem（37.6 字）** | **1.45em（≈0.8 行高）** | **1.82** | 三者平衡，孤字问题消失 |

三个变体当时都出了截图对比，判断依据是：V1 段落仍偏紧、V2 出现孤字换行、V3 平衡。

### 最终改动

```css
main{max-width:min(40rem, calc(100% - 3.5rem))}   /* 46rem -> 40rem，43.3 字 -> 37.6 字/行 */
body{font:17px/1.82 ...}                          /* 1.8 -> 1.82 */
p{margin:1.45em 0}                                /* .95em -> 1.45em，0.53 行高 -> 0.8 行高 */
```

### 考虑过但没做的

| 想法 | 不做的理由 |
|---|---|
| 首行缩进 2em（中文书籍传统）| Markdown 文档里常与列表、代码、表格混排，缩进会显得参差；网页阅读已习惯段间距 |
| 降低正文字面对比度（14.7:1 → ~11:1）| 中文细笔画在低对比下反而更吃力；Kindle 的低对比是为电子墨水屏，LCD/OLED 上收益不明显。若要软化，可把 `--fg` 调到 `#2b3038` |
| 字号/行距调节器 | 与「只读、无设置界面」冲突；真要调，`ctrl +` 也行 |
| 分栏 | 940 窗口宽度分两栏只会更挤 |

## 20. 第二批美化：中西文间距、链接、表格（2026-11-14）

这轮先查资料再改，两条依据：

| 来源 | 结论 |
|---|---|
| W3C clreq issue #712（2025-10 通过）| 建议用 CSS `text-autospace: normal` 给中西文之间加自动间距；clreq 规定间距**不超过¼个汉字宽**，行首行尾、中文标点/括号内侧不加 |
| A List Apart《Web Typography: Designing Tables to be Read, Not Looked At》（Richard Rutter）| **不要把表格拉伸到整栏宽**；**不要斑马纹/底色**（会扭曲逐行阅读）；不要外框；需要分隔时**只用一个方向的细线**；文字左对齐、数字右对齐 |

浏览器支持实测（Edge 157）：`text-autospace` ✅、`text-spacing-trim` ✅、`text-wrap: pretty` ✅、`text-box-trim` ✅、`hanging-punctuation` ❌。
`text-autospace` 的效果实测：8 个汉字/西文边界让一行变宽 10.6px（约 1.3px/边界，符合「不超过¼字」）。

### 改动

| 项 | 做法 | 依据 |
|---|---|---|
| 中西文混排 | `body{text-autospace:normal}`，并在 `pre/code/.code` 上设 `no-autospace`（否则等宽对齐全毁）| clreq #712 |
| 段落末行孤字 | `p{text-wrap:pretty}` | Chromium 117+ 的孤行美化 |
| 多行标题 | `h1..h4{text-wrap:balance}` | 同上 |
| 链接 | 从 `border-bottom` 换成真正的 `text-decoration` + `text-underline-offset:.18em` + 1px 粗细，hover 加粗到 2px | 下划线不占用布局、不与行内代码的胶囊边框打架 |
| 列表符号 | `li::marker{color:var(--muted)}` | 让符号退到信息之后 |
| 表格 | `width:auto` 不拉伸、去掉外框、**去掉斑马纹**、只保留水平细线（用更深的 --table-line）、单元格 padding `.62em .95em`、首末列去内边距 | Rutter 的表格原则 |

### 和上一批的冲突

上一批我给表格加了斑马纹和外框，这一批按研究结论**撤掉**了 —— Rutter 明确说斑马纹「会扭曲数据、牺牲相邻行的可读性」。
但用户要的「表格线深一些」保留了（`--table-line` 独立变量，浅色 1.60:1 / 深色 2.02:1）。

### 代价

表格不再撑满 40rem 文本栏，宽度随内容走 —— 这是研究推荐的（满宽会把数据横向拉开），
但视觉上表格会「结束在页面中间」。想回到满宽只改一行：`table{width:auto}` → `width:100%`。

### 仍未做（需要改渲染器/HTML）

- **数字右对齐**：需要渲染器识别「整列都是数字」并加 class，CSS 无法自动判断
- **宽表格横向滚动容器**：需要在 `<table>` 外包一层 div
- **`<caption>` 支持**：Markdown 本身没有表格标题语法
- **`text-spacing-trim`**：Chromium 默认已启用 `normal`，显式开 `trim-start` 视觉变化很小，暂不动

## 21. 配色：面向长时阅读的调整（2026-11-14）

### 查到的证据

| 来源 | 结论 |
|---|---|
| Yu, Akita 等（2019）平板长时阅读的亮度对比实验 | 在低照度环境（9 / 25 cd/m²）下测了 1:2.5、1:4.5、1:6.5、1:8.5 四档对比，可读性与疲劳**并非越高越好**，存在中间最优区间 |
| Piepenbrock 等《Smaller pupil size and better proofreading performance with positive than with negative polarity displays》| **positive polarity advantage**：亮底暗字的校对表现更好、瞳孔更小（负担更轻）；且**字号越小优势越明显** —— 我们正文 17px 属于偏小字号 |
| 同作者《Positive display polarity is particularly advantageous for small character sizes》| 同上，直接支持小字号正文用亮底 |
| Rello & Bigham (2017)；Betinger & Temelman (2026) 白底 vs 米色底 | 暖色（米色）背景对阅读体验有正面作用；后者的显著差异出现在**阅读困难人群**的身体负担维度，普通人群不显著 |
| 2024 年黄色背景复现实验（*Resounding failure to replicate…*）| **黄色滤镜带来的阅读提升没能复现** → 不做花哨滤镜 |

### 据此定的三条原则

1. **对比度不拉满**：正文/底色从 14.7:1 降到 **约 12:1**（仍是 WCAG AAA 7:1 的 1.7 倍）。
2. **浅色仍是默认**：positive polarity 在小字号下表现更好；暗色用于低照度、减少眩光，跟随系统偏好。
3. **暗色不用纯黑纯白**：底 #15171A、正文 #D6D6D2，避免纯黑的黑洞感和纯白的眩光。

### 新调色板（实测对比度）

| | 改前 | 改后 | 对比度 |
|---|---|---|---|
| 浅色底 | #fbfbf9 | **#FAF8F3**（暖纸）| — |
| 浅色正文 | #22262b（14.7:1）| **#33332E** | **11.96:1** |
| 浅色次要 | #6b7280（4.7:1）| **#6E6A60** | 5.08:1 |
| 浅色强调 | #2f6f4f | **#2C6B4A** | 5.98:1 |
| 浅色表格线 | #cdc9be | **#CBC6B7** | 1.61:1 |
| 深色底 | #16181c | **#15171A** | — |
| 深色正文 | #e6e6e3（14.2:1）| **#D6D6D2** | **12.32:1** |
| 深色次要 | #9aa0a6 | **#96968F** | 6.03:1 |
| 深色强调 | #7fc39a | **#86C79F** | 9.14:1 |
| 深色表格线 | #454b55 | **#464C56** | 2.08:1 |

### 顺带做了系统级无障碍适配（不增加任何设置项）

```css
@media (prefers-contrast: more)  { /* 正文 #15150F、次要 #4A4A42、强调加深 */ }
@media (prefers-contrast: less)  { /* 正文 #45453E、次要 #7A766C */ }
/* 深色模式各有对应的 more/less 组合 */
```

系统偏好「更高对比度」的用户会自动得到更黑/更白的效果，反之亦然 —— 符合项目「零设置界面」的定位。

### 保持不变的

- 单一强调色（墨绿）的气质：没有引入第二强调色
- 代码卡片固定深色，token 颜色不变（实测最低 5.91:1，全部达标）
- 数学公式用 KaTeX 自带颜色，不参与主题变化

## 22. 灰度模式（MDV_GRAY=1）

### 为什么不是「CSS 去色」就完事

原来的代码高亮完全依赖**色相**（关键字红 #ff7b72、字符串蓝 #a5d6ff、函数紫 #d2a8ff、类型绿 #7ee787）。
一旦转灰度，它们的**感知亮度**分别落在 71% / 80% / 75% / 82%，彼此只差几个百分点 —— 肉眼上就是一团糊。
所以灰度优化的核心不是「去色」，而是**重新分配亮度台阶，并用字重/斜体做冗余线索**。

### 做法

1. **新增一套灰度语法主题** `assets/mdv-gray.tmTheme`，token 之间按亮度分级：

| token | 灰度亮度 | 附加线索 |
|---|---|---|
| 关键字 / storage | **100%** `#FFFFFF` | **粗体** |
| 正文标识符 / 变量 | 91% `#E8E8E8` | — |
| 函数名 | 85% `#D8D8D8` | — |
| 数字 / 常量 | 78% `#C6C6C6` | — |
| 类型 / 类 / 标签 | 72% `#B8B8B8` | **斜体** |
| 字符串 | 66% `#A9A9A9` | — |
| 预处理 / 注解 | 56% `#8E8E8E` | — |
| 注释 | 43% `#6E6E6E` | **斜体** |

相邻级别间隔 ≥ 6%，配合粗体（关键字）与斜体（类型、注释、属性），即使全黑白也能一眼分开。

2. **页面也去色**：mdv 在 `MDV_GRAY=1` 时给 `<html>` 加 `class="gray"`，CSS 用一套中性灰变量覆盖
（浅色 #F4F3F0 底 / #1B1B19 字，深色 #121212 底 / #DEDEDE 字），代码卡片变纯灰 #141414，图片 `filter:grayscale(1)`。

### 怎么用

```powershell
setx MDV_GRAY 1          # 永久开启（下次打开生效）
setx MDV_GRAY 0          # 关掉
$env:MDV_GRAY=1; .\mdv.exe spec.md   # 只对本次生效
```

`mdv --status` 会显示当前是否开启。

### 关于系统级颜色滤镜

Windows「设置 → 辅助功能 → 颜色滤镜 → 灰度」是在**显示层**做的后处理，网页无法探测，
所以 mdv 没法自动跟着切。但两者不冲突：

- 只开系统的灰度滤镜：所有颜色被压平，代码会糊（就是上面那个问题）
- **只开 mdv 的 MDV_GRAY=1**：得到一套为灰度设计过的亮度结构（推荐）
- **两者都开**：同样是灰度，但 mdv 这边已经是灰的，滤镜等于空转 —— 结果与只开 mdv 相同

### 视觉验证

当时用 `MDV_GRAY=1 --shot` 出了浅色/深色两张灰度截图对比；截图不进仓库。

## 23. 三档配色按钮：正常 / 灰度 / 暗色

### 前提：先把 token 颜色从内联样式搬到 CSS

原来 syntect 的高亮是**渲染时写死内联 `style="color:#ff7b72"`** 的，页面里再加按钮也改不动它。
所以先做了一次改造：

- 渲染器把颜色映射成语义类名：`<span class="tk tk-kw">`、`tk-str`、`tk-num`、`tk-fn`、`tk-type`、`tk-meta`、`tk-comment`、`tk-var`
  （映射表 `token_class()` 依据我们自己那份 `mdv-dark.tmTheme` 的色值，未知颜色仍回落内联色）
- 颜色改由 CSS 变量 `--tk-*` 提供，三种模式各一套 → **切换不需要重新渲染，代码块同步变色**

### 三档模式

| 按钮 | class | 说明 |
|---|---|---|
| 正常 | （无）| 彩色，明暗**跟随系统** `prefers-color-scheme` |
| 灰度 | `.mode-gray` | 中性灰页面 + token 按**亮度台阶 + 粗体/斜体**区分；明暗仍跟随系统 |
| 暗色 | `.mode-dark` | 强制彩色暗色（无论系统设置）|

选择写进 `localStorage['mdv.mode']`（和滚动位置一样，mdv 侧不落文件）；
首帧前由 `<head>` 里的小脚本先把 class 定好，**不会闪一下才变色**。
`MDV_GRAY=1` 仍然有效，作为「默认就是灰度」的初始 class。

### 踩到的坑

首帧脚本一开始无条件写 `document.documentElement.className = cls`，localStorage 没值时写空串 ——
把服务端渲染进来的初始 class（`MDV_GRAY=1` 的 mode-gray）**直接清掉了**。
改成「只有用户明确选过才覆盖」才正确。这个 bug 是靠「暗色截图和灰度截图字节数完全一样」发现的。

### 按钮样式

右上角胶囊形按钮组，平时 `opacity:.38`（不抢注意力），hover/focus 变实；
选中项用强调色 16% 混合底；`aria-pressed` 由脚本维护，键盘可达；打印时隐藏。

### 验证

- `aria-pressed` 由 JS 正确写入（dump-dom 实测 normal=true、其余 false）
- 三种模式各出一张 `--shot` 截图对比（截图不进仓库）
- 灰度模式下 token 亮度台阶生效：关键字 100% 粗体 / 类型 72% 斜体 / 注释 43% 斜体

## 25. 分发用的脱敏构建（2026-11-14）

**问题**：默认 `cargo build --release` 产出的 exe 里含 **58 处** `C:\Users\<用户名>\.cargo\registry\src\...\lib.rs`，
这是依赖 crate 的 **panic 位置字符串**（`strip = true` 只去符号表，去不掉这些字符串字面量），
等于把 Windows 用户名一起分发出去。实测泄漏项：用户名 58 次、`.cargo` 58 次。

**做法**：重映射编译期路径（`scripts/build-release.ps1`）。

- 用 `CARGO_ENCODED_RUSTFLAGS`（`\x1f` 分隔）而不是 `RUSTFLAGS`：
  后者按空格切分，仓库路径里的空格（`md文件查看器 设想`）会被拆成两个参数，报
  `error: --remap-path-prefix must contain '=' between FROM and TO`（踩过）。
- 两处映射：`<cargo>\registry → /cargo-registry`、`<repo> → .`。
- 脚本结束前自检：把用户名、计算机名、仓库目录名、`.cargo` 等针串扫一遍二进制。

**结果**（同一份代码）：

| 针串 | 重映射前 | 重映射后 |
|---|---|---|
| Windows 用户名 | 58 | **0** |
| `.cargo` | 58 | **0** |
| 计算机名 / 仓库目录名 / `AppData` / `Desktop` | 0 | 0 |
| exe 大小 | 3,639,296 | 3,638,784（-512 B）|

功能不受影响：渲染 28.5 ms、截图、文件关联、`--status` 全部正常。
